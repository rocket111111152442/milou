# WAVERTI — Rapport de finalisation (31 octobre 2026)

Branche `claude/upbeat-ritchie-sll5u2`. Aucun paiement réel, aucune dépense, aucun service payant souscrit,
aucun DNS modifié, forfait Vercel inchangé (Hobby), aucun autre projet modifié.

**Niveaux de vérification** utilisés dans tout le rapport :
- **Développé** : code écrit, pas de test dédié.
- **Local** : testé automatiquement sur la machine de développement (vrais PostgreSQL, Chromium, serveurs HTTP locaux).
- **CI** : testé automatiquement par GitHub Actions sur une vraie machine Linux, Windows ou macOS.
- **Externe** : vérifié avec le vrai service (Stripe, Brave, Resend…).
- **Production** : vérifié en production.
- **Non terminé**.

Aucune fonctionnalité n'est au niveau **Externe** ni **Production** : aucune base de production, aucune clé de
test Stripe, Brave ou Resend n'est disponible dans cet environnement.

## 1. État général

WAVERTI est prêt pour une **bêta privée technique** dès qu'un serveur PostgreSQL et le worker seront installés.
Le parcours complet fonctionne de bout en bout en local et en CI (site, comptes, double authentification,
surveillances, alertes, applications de bureau sous Windows et Linux, PWA dans Chromium). Ce qui manque est externe : le serveur,
les clés des services en mode test, la configuration du webhook Stripe, la validation juridique.

## 3. Windows

Workflow `Waverti Desktop — plateformes`, exécution 41198398709 (commit `714a66e`) : **réussie**.

- E2E du **binaire réel** piloté par WebDriver (WebView2 + msedgedriver), contre le site et PostgreSQL lancés sur
  la machine Windows : liaison de l'ordinateur par code validé dans le navigateur, accord explicite horodaté,
  contrôle d'une page **exécuté par l'ordinateur**, résultat et alerte remontés au serveur, remise de la
  notification à l'application, pause transmise au serveur, déliaison (jeton révoqué). **5/5** [CI].
- Correctif WebView2 : il ne s'applique qu'aux compilations de développement Windows (`debug_assertions`) ; les
  versions destinées aux utilisateurs ne lisent pas ces variables.
- Installateur **NSIS** (`Waverti_0.1.0_x64-setup.exe`, 2,5 Mo) : installé sans droits administrateur, lancé
  (10 s), désinstallé [CI]. **MSI** (`Waverti_0.1.0_x64_en-US.msi`, 3,2 Mo) : installé (installation
  machine), lancé, désinstallé [CI, exécution 41203248803 sur `c2a8e55`, après correction du script de contrôle].
- Tests et lint Rust sous Windows [CI].
- Installateurs (artefacts de test **non signés**, conservés jusqu'au 7 novembre 2026) :
  https://github.com/rocket111111152442/milou/actions/runs/41203248803 → « waverti-windows-NON-SIGNE-test-uniquement »
  (et « waverti-macos-… », « waverti-linux-… »). Connexion GitHub requise pour télécharger.
  Captures d'écran de l'E2E : « windows-e2e-captures ».
- **Non vérifié** : PC Windows réel (SmartScreen bloquera un installateur non signé, antivirus, proxy),
  affichage visuel de la notification par Windows, coupure réseau pendant un contrôle sur Windows (la reprise
  hors ligne de l'agent est testée en unitaire), inscription et double authentification **dans** l'application
  (l'application ne gère pas de mot de passe : la liaison se fait dans le navigateur, où ces parcours sont testés).
- **Mises à jour** : extension Tauri désactivée par défaut, signature minisign obligatoire. Point bloquant
  identifié : le workflow de publication crée des versions *prerelease*, que l'adresse `releases/latest` ignore.
  Avant d'activer les mises à jour, il faudra publier en version normale et générer la paire de clés de
  signature (gratuite). Aucun certificat de signature de code n'a été acheté.

## 6. PWA iPhone / Android

Vérifié dans Chromium [Local + CI] : manifeste et icônes, service worker, page hors ligne, bandeau hors connexion,
aucune page privée ni réponse d'API en cache, caches vidés à la déconnexion, espace client utilisable sur un
téléphone émulé (tableau de bord, surveillances, création, alertes, historique, paramètres, abonnement), sans
défilement horizontal. Nouveau : une nouvelle version du site est **proposée** (« Recharger ») au lieu d'être
imposée, et le cache est borné.
Un défaut de cette modification a été **détecté par les tests et corrigé** : la page se rechargeait d'elle-même à
la première installation et effaçait les formulaires.
**Non vérifié** : Safari / iPhone réel et téléphone Android réel (WebKit n'est pas disponible dans cet
environnement). **Notifications push : non terminées** (réception préparée dans le service worker ; envoi et
abonnement non développés). Sur iPhone, les notifications web exigent iOS 16.4+ et l'ajout à l'écran d'accueil.
Les surveillances ne s'exécutent jamais sur le téléphone : elles sont faites par les serveurs.

## 7. Surveillance des pages (moteur A)

Nouveaux scénarios sur une boutique de test que nous contrôlons (aucun site tiers) [Local + CI] :
- prix sous un seuil : une seule alerte, puis une nouvelle après remontée et nouvelle baisse ;
- baisse d'au moins 10 % : ni la hausse ni une baisse de 4 % n'alertent ;
- rupture puis retour en stock : une seule alerte ;
- apparition d'un texte, modification significative ;
- erreurs 503 et 404 enregistrées sans fausse alerte ; site lent mais disponible traité comme disponible ;
- historique complet des prix.
Déjà couverts : extraction (JSON-LD, microdonnées, texte), fréquences, file hybride ordinateur / serveurs,
aucun double contrôle, reprise après panne d'un worker, robots.txt, SSRF.

## 9. Surveillance Business (moteur C)

[Local + CI] Vérification de propriété (DNS / fichier), contrôle HTTP chaque minute, confirmation par second

## 10. PostgreSQL et authentification

6 migrations reproductibles sur une base vide, RLS (`app_user`), tables d'identité inaccessibles aux requêtes
utilisateurs. Inscription, vérification d'adresse, connexion, mot de passe oublié, double authentification, codes de
récupération, anti-rejeu, sessions, export et suppression RGPD [Local + CI]. Sauvegarde puis restauration avec
contrôle des comptes, surveillances et RLS [Local] ; sauvegarde tronquée refusée, sauvegarde modifiée refusée par
somme de contrôle, aucune base temporaire laissée [Local]. Worker : démarrage, arrêt propre, signaux de vie,
reprise après interruption, file et priorités [Local + CI]. **Non terminé** : serveur de production (non souscrit).

## 11. Stripe et webhooks

- Route réelle : `POST /api/stripe/webhook` ; signature obligatoire, événements dupliqués traités une fois, ordre
  indifférent, 500 renvoyé en cas d'échec pour que Stripe réessaie [Simulé].
- Scénarios en mode test simulé : essai 72 h avec carte, conversion, renouvellement, résiliation immédiate et
  programmée, changement de formule, échec de paiement avec délai de grâce, arrêt des surveillances à
  l'expiration, blocage d'un second essai avec la même carte.
- Clés de recherche attendues : `waverti_plus_monthly`, `waverti_pro_monthly`, `waverti_max_monthly`,
  `waverti_business_monthly`, `waverti_business_extra_site_monthly`. **Les identifiants `price_` réels n'ont pas
  été lus** : la clé Stripe n'est pas disponible ici. `pnpm stripe:prices` fonctionne (vérifié contre
  stripe-mock ; lecture seule avec une clé live).
- **URL définitive du webhook** : `https://www.waverti.com/api/stripe/webhook`. Tant que la protection Vercel est
  active : `https://www.waverti.com/api/stripe/webhook?x-vercel-protection-bypass=SECRET` (procédure complète :
  `docs/DEPLOYMENT.md` § 4). La protection n'a pas été désactivée.
- Le site refuse toute clé `sk_live_` sans `WAVERTI_ALLOW_LIVE_PAYMENTS`.

## 13. Sécurité

Vérifié [Local + CI] : authentification, sessions (`__Host-`, jeton haché), TOTP et anti-rejeu, codes de
récupération, droits administrateur (404 pour les autres, double authentification exigée), isolation des clients
(RLS + E2E), SSRF et validation des URL (résolution DNS contrôlée), limitation des tentatives, webhooks signés,
secrets uniquement côté serveur, CSP, en-têtes de sécurité, requêtes paramétrées, erreurs génériques, journal d'audit.
Points ouverts : CSP avec `'unsafe-inline'`, `freezePrototype` désactivé côté desktop, secret de contournement
Vercel visible dans l'URL du webhook, plafond global Brave. **Audit indépendant nécessaire** avant l'ouverture
publique : test d'intrusion de l'authentification et de l'isolation, revue de l'agent desktop (exécution sur
les postes des clients), revue de la configuration du serveur PostgreSQL.

## 14. Coûts techniques

Détail : `docs/COUTS.md` (mesures, tarifs vérifiés, hypothèses séparés). Au maximum des quotas, aucune formule
n'est déficitaire en coût variable. Projection pour 1 000 clients identiques : coût technique ≈ 1 037 € (Plus),
3 827 € (Pro), 7 180 € (Max), 4 974 € (Business) par mois. Ce sont des **marges techniques**, pas des bénéfices.
Deux constats importants :
1. **Stockage de l'historique** : jusqu'à 2 à 3,7 To / an pour 1 000 clients Max. La compaction ajoutée
   le ramène à ≈ 0,9 To / an (mesuré : 0,7 Ko par ligne compactée), sans changer l'historique affiché.
2. **Brave** reste le principal coût variable ; le plafond global de 50 € / mois doit être relevé avant le
   lancement, sinon les recherches de tous les abonnés s'arrêteraient.

## 19. Points bloquants

1. Pas de serveur PostgreSQL / worker (achat à décider) : rien ne tourne réellement pour des utilisateurs.
2. Pas de clés **de test** Stripe, Brave, Resend dans un environnement utilisable : intégrations non vérifiées
   avec les vrais services.
3. Webhook Stripe : secret de contournement Vercel et destination Stripe à créer (§ 11).
4. Installateurs non signés (SmartScreen, Gatekeeper) et mises à jour automatiques non activées.
5. Notifications push mobiles non développées.
6. Validation juridique (CGV, confidentialité, mentions légales à compléter) avant tout encaissement.
7. Vercel Hobby interdit l'usage commercial.

## 20. Actions à effectuer par LULLIN WEB

1. Choisir et commander un serveur (worker + PostgreSQL, disque dimensionné pour l'historique) quand vous le
   déciderez ; ensuite : `docs/DEPLOYMENT.md` § 1 et § 3.
2. Renseigner sur Vercel : `DATABASE_URL`, `WAVERTI_ENCRYPTION_KEY`, `WAVERTI_HASH_PEPPER`,
   `NEXT_PUBLIC_APP_URL`, `EMAIL_FROM`, `ADMIN_REQUIRE_MFA=1` ; clé Brave sur le serveur du worker.
3. Stripe (mode test) : `pnpm stripe:prices` pour lire les `price_` réels, secret de contournement Vercel,
   destination webhook, `STRIPE_WEBHOOK_SECRET`.
4. Resend : vérifier le domaine d'envoi (enregistrements DNS chez Hostinger).
5. Bêta privée : créer son compte sur le site, puis `pnpm beta:grant adresse --plan pro --days 30 --reason "…"`.
6. Relever le plafond `budget.monthly_api_eur` selon le nombre de testeurs.
7. Tester sur un vrai PC Windows, un vrai Mac, un iPhone et un téléphone Android.
8. Validation juridique ; décision Vercel Pro et certificats de signature (payants) avant le lancement.
